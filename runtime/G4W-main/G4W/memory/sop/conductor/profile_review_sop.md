# 用户画像维护 SOP（conductor 专用）

> 最终画像**只能由 conductor（你自己）维护**——用你的语气、你的视角。
> L4 worker 只负责产出素材草稿；草稿是交接物，不是最终画像。

## 触发时机

每次 L4 worker 三阶段完成（`worker-final` 汇报轮），在本轮**汇报之前或之后**顺势维护画像：
读草稿与现有画像 → 决定更新/修改/保持不变 → 需要时落盘。

## 读取内容

1. **素材草稿**：`runtime\G4W-data\memory\conversations\<当前账号>\summaries\history_insight\user_profile.draft.md`（finalize 已校验落盘的正式交接物；**只读 draft，不要读 subagent_output 里的原始 candidate**）
2. **现有画像**：同目录 `user_profile.md`（你之前维护的叙述版；**不存在则为首版**）
3. 必要时参考：`memory\users\<账号>.md`、`memory\operational\<账号>.md`（确定性事实与操作偏好）

## 维护规则

1. **用你的语气**：这是你（conductor）对用户的叙述——用你与用户之间既定的人设与语气（你是谁、怎么称呼用户、有什么口癖，由你的角色配置决定），保留亲昵与情感，不要写成报告体。
2. **保留全部信息点**：现有画像里的信息与草稿里的新素材都要覆盖，**不删减**（内容只会增改，不会丢失）。
3. **变化表述保留旧信息 + 时间**：特征变化写成"他以前…；MM-DD 起…"，旧信息不丢、新状态明确、时间清晰。
4. **首版**：无现有画像时，以草稿 + 历史资料为素材写完整版（约 3000~9000 字，像你平时说话那样）。
5. **保持不变**：草稿明确"无画像相关变化"或本轮素材不足以改动时，**不要动文件**——不为了更新而更新。

## 落盘

- 有变化：`file_write` 覆盖 `user_profile.md`（保留你已有的标题结构）
- 无变化：不写文件

## 汇报

向用户汇报 L4 结果时**一句带过**画像维护情况（如"画像已同步"或"画像没有变化"），不要展开全文——用户需要时可自己在看板查看。

## 红线

- 禁止编造：没有素材证据的特征不写。
- 不写 agent 内部经验（能力/教训）到画像——那是记忆，不是用户画像。
- 临时事件不进画像（吃了个苹果不算；看房/升学/健康才算人生大事）。
